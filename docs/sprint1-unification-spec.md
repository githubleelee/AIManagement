# Sprint 1 统一与验收规格

## Problem Statement

多人分支开发留下了不同时间点的集成说明、前端路线描述和代码注释。接手者难以判断 Sprint 1 的用户故事、接口和页面分别处于设计、实现、主干集成还是验收阶段。当前代码已具备主要纵向链路，但最新同步后尚未运行本轮验收，不能仅凭文档判断项目整体已完成。

## Solution

建立一个可追溯的 Sprint 1 当前状态基线，按登录、项目权限、需求与敏感可见性、任务管理等用户流程核对实现和契约；修正文档与注释中的过期状态；运行类型检查、接口测试、生产构建和手工流程走查；最后整合已验证的收尾分支并更新交接记录。

## User Stories

1. 作为接手开发者，我希望看到带分支和提交号的单一当前状态表，以便判断每项功能是否实现和集成。
2. 作为接手开发者，我希望冻结契约、历史记录和当前状态有清楚标签，以便不会把过时记录当成现状。
3. 作为团队成员，我希望每个用户故事都能映射到接口和页面，以便快速发现漏接或重复实现。
4. 作为登录用户，我希望登录、令牌和受保护页面遵守统一错误与回跳契约，以便认证链路行为一致。
5. 作为项目成员，我希望项目隔离、角色限制和服务端鉴权在所有项目操作中一致，以便跨项目数据不会泄露。
6. 作为项目经理，我希望创建、编辑和查看目标、活动、故事的字段及层级符合契约，以便需求链路可预测。
7. 作为项目成员，我希望敏感故事和任务在列表、详情、计数和过滤中遵守同一可见性规则，以便无法通过不同查询路径探测数据。
8. 作为项目经理，我希望创建、编辑、删除任务和查看任务列表使用统一字段、状态、日期和错误口径，以便任务流程贯通。
9. 作为前端用户，我希望页面实际状态、路由和 API 前缀与当前文档一致，以便直达和刷新页面时行为一致。
10. 作为评审者，我希望看到最新类型检查、接口测试、构建和关键流程走查证据，以便判断项目是否可运行且符合契约。
11. 作为团队成员，我希望经过验证的收尾提交以团队约定的方式进入主干，并更新交接说明，以便下一位开发者从可信基线上继续。

## Implementation Decisions

- 仅处理 Sprint 1；不把 US-04、US-06 及后续产品能力混入本轮验收。
- 以接口契约文档为行为权威，以当前状态表为集成进度权威；基线及历史集成文档保留为历史来源并标注适用时间/提交。
- 使用现有 HTTP 接口测试作为最高且主要的测试 seam；不新增模块内 mock seam。
- 验证每条垂直链路：认证与项目访问、需求和敏感可见性、任务操作与查询、前端路由/API 接入。
- 修复只在验证发现偏差后实施；契约变更遵循团队现有的提出、受影响方确认、单一负责人修改、通知流程。
- 先在当前收尾分支完成核对和验收，再按团队约定整合；不要通过未经确认的强制重置或覆盖来同步分支。
- 不将课程表 6–8 或录屏作为“可运行与契约统一”的阻塞验收项；如需课程提交，单独跟踪。

## Testing Decisions

- 好的验收覆盖外部请求/响应、持久化可见结果和页面关键行为；不以内部实现细节作为通过条件。
- 复用 Vitest + HTTP 测试上下文和隔离 SQLite；已有测试应保持原有断言语义。
- 核对认证、项目成员/角色、需求层级、故事与任务敏感可见性、任务 CRUD/列表/负责人过滤。
- 交付前运行 `npm run typecheck`、`npm test`、`npm run build`，再手工走查代表性角色流程和页面深链。
- 在未运行并记录命令结果前，不得宣称类型检查、测试、构建或端到端验收通过。

## Out of Scope

- US-04 看板、甘特图、成员负载、个人待办、风险视图、AI 能力和通知等后续产品功能。
- 真实用户部署、生产环境运维和完整安全认证；本轮只验收 Sprint 1 既定契约。
- 课程表格和演示录屏的撰写；可作为独立课程交付工作另行安排。
- 未经检查的全仓重构、接口重设计或数据库 schema 改动。
