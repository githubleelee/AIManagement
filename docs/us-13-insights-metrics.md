## 1. 本批次做了什么

`src/modules/ai-insights/`：

| 文件 | 作用 |
|---|---|
| `types.ts` | 四类指标的类型与线上常量（含 D §2.1 的四个场景值） |
| `aggregate.ts` | **纯聚合层**：只吃「计数事实」，无 Prisma、无 I/O |
| `metrics.ts` | **取数层**：判权 → 取可见性作用域 → 查库 → 组装计数事实 → 附口径声明 |

分两层不是风格偏好：取数层**只取计数**，因此标题 / 描述 / 人名**没有机会**进入结果
（由类型保证）；口径边界可以用不建库的用例逐条钉住。

配套改动（评审 P1）：**冻结口径的纯函数上提到 `src/modules/analytics/caliber.ts`**
（`planTimeDaysOf` / `healthOf` / 两个阈值常量 / `CALC_TIMEZONE` / `isoToday` / `roundTo`），
`analytics/service.ts` 与本模块都 import 它。

## 3. 口径来源（AC6：与 #30 一致，不各自定义）

| 类别 | 口径 | 来源 |
|---|---|---|
| 进度 | 已关闭 ÷ 总数（`DONE` 不计入）；计划时间进度含首尾；偏差 = 计划 − 实际（pp）；≤10 / ≤25 / >25 分级 | **`analytics/caliber.ts` 的纯函数**（`planTimeDaysOf` / `healthOf` / 阈值常量） |
| 计划窗口 | **可见窗口**：分子、分母与计划区间同源同窗口 | DECISIONS `analytics.dashboard-window-basis` |
| 质量 | 驳回数 / 重验次数 = Σ max(0, 该任务记录数 − 1) / 驳回率（分母 0 → `null`）/ 卡住任务数 | #29 的 `AcceptanceRecord` 与任务六态（本模块定义并写进 `basis`） |
| 风险 | 未解决 = 未处理 + 处理中；`byLevel` 只统计未解决 | 与 #30 的关闭阻断**同源**（`RESOLVED` / `CLOSED` 不阻断） |
| 效率 | 负载 = 负责人名下非 `CLOSED` 任务数（**含 `DONE`**） | #27 与 DECISIONS `scheduling.load-aggregation-baseline` |

**为什么不复制进度公式**：那份公式刚被独立评审修掉一个浮点边界缺陷（H2，
`(0.4−0.3)×100 = 10.000000000000004 > 10` 把正好落在阈值上的情形错分）。复制一份等于把
缺陷搬进一个没有交叉校验用例的新模块。

**为什么不是「import 一个 service」**（评审 P1）：原先 import 的是 `analytics/service.ts` ——
实质不越界（无环、只取纯函数、不调 `buildDashboard`），但字面违反 I-9「模块之间不导出可被
调用的 service 函数」。整改办法是把**口径与 I/O 分层**（上提 `caliber.ts`），而不是复制公式、
也不是给 I-9 开豁免：公式仍只有一份，依赖边不再是 service → service。

**交叉校验的证明力边界**（评审 P2，如实登记）：`metrics.test.ts` 的两条交叉校验把本模块结果
与 `GET /projects/:projectId/dashboard` 对表，但两边调**同一个** `healthOf` ⇒
「健康度 / 阈值相等」这几条对**口径漂移是恒真的**。它们真正证明的是**取数层等价**
（分子、分母、计划窗口由两边各自独立查询）；口径本身由 `aggregate.test.ts` 的绝对数值
边界用例、以及交叉校验里补的**绝对值锚点**（如非 PM：5 个可见任务 / 2 个 CLOSED / 计划 0.5
⇒ 偏差正好 10pp ⇒ 健康）兜住。

## 4. 数据边界（设计 §5.1 第 2 条）

- 结果**只含计数 / 比率 / 天数**：不含任务标题、描述、驳回原因原文、成员姓名或账号；
- 成员维度**只给匿名键** `memberKey = sha256("ai-insights:member:" + projectId + ":" + userId)`
  前 12 位十六进制：同项目同一成员稳定，跨项目不同（防跨项目串联）。
  ⚠️ **盐就是 `projectId`**，而端点 7 会把成员 `userId` 给到项目成员 ⇒ **同时持有成员名单的
  调用者可逐个枚举匹配**（评审 P4 更正了原先"不可逆推"的过强说法）。它对外部与端口不透明，
  不是"任何前提下都不可逆"；要真正不可枚举需**每项目随机盐**（要建表，本批不建表，登记为
  后续申请项）；
- 可见性在**查询层**过滤（契约 I-6）：任务 / 验收 / 风险三侧拼同一个作用域；
  敏感风险继承所关联任务的可见性（#30 批复第 7 项）；
- **只读**：不写库、不写审计、不发事件；5 条查询放进**同一个事务**（评审 P3），
  使四类数字取自**一个读取窗口**，不会出现"互相矛盾的一组数"。
  ⚠️ **前提（复审 P-3 补）**：这条"单一快照"保证来自**数据库的隔离级别**，不是 `$transaction`
  本身 —— SQLite 事务可串行化（延迟 BEGIN、首读建快照），故成立；若迁到默认 READ COMMITTED
  的库（Postgres / MySQL），事务内每条语句各取新快照，本条保证**失效**，须改用
  REPEATABLE READ 或把相关读取合并成一条语句。

上述四条都有用例：结果里搜不到任何标题 / 姓名 / 账号 / `taskId` / `riskId`，且有一条
**递归白名单扫描**（遍历结果里每个字符串，只放行匿名键 / 常量 / 日期 / 口径文案）——
将来新增一个带原文的字段会自动被抓住，不必靠人记得加断言。

## 5. 敏感对象与聚合（2026-10-19 裁定，评审 B1）

设计 §5.1 第 4 条的「敏感对象不进入任何一个聚合」与第 3 条的「按 C6 基数取数」存在字面冲突；
独立评审把它列为**阻断项**，理由是一旦接 #31 端口，共享记录里的 `containsSensitiveData: false`
会与事实相反。裁定如下：

- **本模块的聚合按 C6 基数**：PM 含敏感对象、其余按可见范围 —— 与 #30 的仪表盘**同源**，
  因此 AC6 的「口径一致」成立、交叉校验也才有意义；
- **给 #31 端口的输入不是这份结果**：生成层要另做「AI 参与子集」（排除敏感对象），并如实记
  `sourceCount` / `includedCount` / `excludedSensitiveCount`（D §2.3 本来就要求「如实区分
  全基数与 AI 实际参与子集」）；
- **非 PM 不得输出 `excludedSensitiveCount`** —— 那会泄漏敏感对象的存在性（与 #30 的
  「非 PM 看不到阻断项 ≠ 项目能关」同一类纪律）；
- ⇒ 在生成层落地前，**不得**用本模块的输出直接声称 `containsSensitiveData: false`。

## 6. 已知限制（算不出来的，如实登记在响应的 `unavailable` 里）

1. `quality.avgAcceptanceDays` **恒为 `null`**：库里没有「任务何时进入待验收（`DONE`）」
   的时间戳。用「创建 → 验收」冒充会把整个执行时长当成等待时长，故不用 0 或替代值冒充。
2. `doingTasks` / `pendingAcceptanceTasks` 只给**数量**（积压规模），给不出**滞留天数**。
3. **敏感对象的 AI 参与子集**属生成层（见 §5），本票不产出。
4. **不设「超过 N 即过载」阈值**：阈值属业务裁定，不在聚合层发明。
5. `Σ byMember.openTasks ≠ total − closed` 的情形是**口径限制**：只统计当前 `ProjectMember`，
   而「退组负责人名下的任务」口径在 `role-b-workload-design` 里尚未定案（评审确认，非缺陷）。
6. 验收记录的 `taskId` 未校验与 `projectId` 同项目：PM 视角下若存在跨项目脏数据会被计入
   （评审 S5，理论边角，已登记）。
7. **本批次无端点**：调用方是未来的生成层；用例直接调取数层函数（唯一走 HTTP 的是
   #30 的仪表盘，用于交叉校验）。
