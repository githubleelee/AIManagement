### 一、数据契约 §5：七问逐项答复

| 问题 | C 的答复 |
|---|---|
| 1. 最小字段与共享字段合并 | 原集合基本接受；服务端规则复核补 `acceptorUserId`；成员读取至少含 `userId/role`，用于成员集合与权限复核；补任务—里程碑关联。`title` 仅按展示需要取，`description/progress/blockedReason` 不作为首批模型必需字段；`createdAt` 不充当更新版本。排敏须同时覆盖任务及关联故事的敏感/可见性，过滤在查询层完成，不能先取正文再内存过滤。建议/处置字段交 D/B 合并共享契约，不建 C 专属表。 |
| 2. 受众基数及返回位置 | 接受 `visible-range / pm-protected / ai-input` 的区分。建议分成独立 DTO/序列化出口，而不只给同一对象打标签：PM 内部基数与排除敏感数不得进入模型。AI 负载按实际非敏感参与任务重算，非 CLOSED 含 DONE。非法或缺失必要信息的记录不得悄悄删去后把输入称为完整；记录不可用/不完整原因，只在授权的内部上下文处理。不新增过载阈值。 |
| 3. 跨子集约束 | 模型不接收隐藏端点、隐藏边、隐藏计数或占位提示。服务端在统一鉴权后核验所有与候选变更有关的真实 FS 约束（含未改期相邻任务），不能删除跨子集边后当作无依赖。约束读取必须完整且合法；不足则不允许正式应用。相关敏感约束只在受保护服务端验证，不存其正文到输入快照，也不外发；如需支持此校验，请 B 核对最小私有摘要及读取权限边界。 |
| 4. 快照/asOf | 同意与事务方案合并；任务五字段不够。范围含参与集合、日期/状态/负责人/验收人、成员及相关角色、有效参与范围、FS、任务—里程碑关联与日期、非 CLOSED 负载来源、数据完整性。`asOf` 保持 ISO UTC，业务日期保持 YYYY-MM-DD/Asia/Shanghai；`asOf` 是一致读取的时间标记，不是锁或版本。模型调用耗时不改变它，另记生成时间。 |
| 5. FS/里程碑形状与可用性 | 接受最小 FS 边和里程碑形状；补关联映射。对齐当前 #26 实际字段，不另造平行领域模型。保留“有值/不可用”两态，已知空只能表示为可用且空；截断/完整性另列元数据，不把它混成第三种 Availability 状态。正式应用所需集合不可用、截断或完整性未知时 fail-closed；不虚构里程碑。 |
| 6. 读取方式 | C 建议首批采用独立 ai-scheduling 目录内、经注入 DB 的只读投影，不要求 B 再建聚合服务；必须支持同一事务中的复读，不能以多次 HTTP GET 充当一致快照。先统一 can()/visibilityScope()，查询层合并项目、可见性及排敏条件；私有约束读取与外发 DTO 严格分离。不调其他域 service。纯规则复用按事务提案收口；若 B 要求 shared 只读端口，C 可按同等语义适配，不先冻结方法名。 |
| 7. 应用后派生更新 | 接受。仅改 TODO 的 planStart/planEnd，不写甘特、负载派生结构，不改依赖或里程碑。成功后刷新真实读取视图；纯改日期不改变按非 CLOSED 计数的负载数，不能把“负载数必须变化”写成验收条件。 |

### 二、事务提案 §12.1：十二问逐项答复

以下涉及实现选择的内容均为 **C 建议，待 B/D 核对**，不扩展已批准规则。

| 编号 | C 的建议/答复 |
|---|---|
| C1 动作/scope | 共享处置 Action 已定，不再新增 scheduling 专用处置 Action。生成、读取、审计与处置区分授权语义，#32 全部 PM-only；具体动作命名由 B 收口。优先复用 project ObjectRef，建议 ID 的存储归属必须服务端解析并核对。所有 #32 动作在 can() 显式拒绝非 PM，不能落默认允许。 |
| C2 事务类型 | 建议选结构化窄 DB 接口 Pick，而非暴露整个 PrismaClient 联合；按最新实现实际用到的 delegates 列出，允许 root 与 tx。B 改 authz 工厂及内部 helper；C 在获写窗口后改 assertTaskAssignment。can()/visibilityScope() 公开参数和决策语义不变；必要类型随之调整，不使用 any/强制断言绕过类型。 |
| C3 写入口/统一能力 | 建议受控处置入口位于 ai-scheduling；统一计划写能力在获授权 task/rules.ts 范围内提炼，由手工 PATCH 和本域应用共用。跨域经 B 声明的 shared 端口及 app 注入，不直接导入 task service。候选能力是“接受调用方事务 DB、项目及日期变更集合”，不得自己提交另一事务。基础规则共用；TODO-only、快照、FS 等 #32 限制由本域在同一事务叠加，不强加给所有手工 PATCH。 |
| C4 唯一处置 | 建议共享存储以 suggestionId 的唯一最终处置约束兜底，配合 pending→最终状态的 CAS；二者与任务写、成功审计在同一事务。唯一约束由 B 迁移落地，共享端口保证原子声明处置；不能先独立落最终状态再改任务。不同请求并发只能一个提交，不能仅靠 SQLite 单写者假定正确。 |
| C5 错误映射 | 保留 401/403/404 既定语义。建议过期、已被不同请求处置、幂等键复用但内容不同映射 409，并有可区分的业务原因；同项目越建议范围、非法日期/越字段等沿用既有 400 校验错误。必要数据不可用/不完整应明确失败而非空集成功，具体错误 code 与 #31 公共错误表对齐，不在本评论创造已冻结 code。 |
| C6 幂等键 | 建议增加独立处置请求标识（客户端一次逻辑处置生成，重试保持），并存规范化 payload 摘要；不只按“内容相同”判断同一请求。这与 B 的纯摘要候选不同，理由是能区分用户独立操作和网络重试，不需要新中间件；字段及唯一约束纳入共享建议存储，请 B/D 核对。 |
| C7 fingerprint | 建议将完整非敏感最小快照保存在受保护共享记录中；服务端私有约束只保留批准的必要摘要，不保留敏感正文。稳定排序和序列化后摘要，候选 SHA-256；算法/规范标识属于该快照协议，不给所有业务表增加全局 version/hash 列。完整范围见数据答复 4；摘要不是并发锁，仍需事务内复读及竞态测试。 |
| C8 有效权限 | 以确认时实时 can()/visibilityScope() 为准，不拿生成时权限授权。已无 #32 操作权直接拒绝、不读回历史；仍有权但影响参与范围/约束/成员的相关权限或来源变化，整份过期。无关项目/对象变动不全局作废。并发撤权以事务一致性与提交顺序界定：不承诺“事务鉴权后任何微秒内撤权都能中断已在途操作”；请 B 核对具体实现如何保证已提交撤权在后续处置/重试生效。 |
| C9 失败证据 | 成功审计与应用同事务。业务校验/应用失败在回滚后独立记失败证据，可复用 AuditLog 的明确失败 action；认证/鉴权拒绝建议走安全日志，避免为不存在或无权项目写伪业务记录。两类具体落点由 B 核对现有能力，不新造基础设施；仅最小元数据/关联标识，不写提示词、敏感正文或密钥。证据写入失败须可观察，不能冒充留痕成功。 |
| C10 复核顺序 | 接受：最小 id/projectId 归属解析→事务内 can()→受保护建议/处置读取→幂等重放→无最终处置时复算来源及完整性→规则与写入。入口项目不信任客户端；归属不匹配/不可见统一 404。重放在快照复核之前，避免自身成功更新被误判过期。拒绝处置不写任务；“过期建议能否仍拒绝、是否跳过日期校验”请 B/D 在共享状态机明确，不让日期应用校验阻塞所有拒绝操作。 |
| C11 同一请求身份 | 候选作用域：项目+建议+actor+处置请求标识；规范化内容含处置类型、日期集合及理由，顺序不影响等价。仍有权的同 actor/同标识/同内容返回首次结果；同标识异内容冲突；另一 PM 即使 payload 相同也不是同一请求；同 actor 不同标识也不自动视为重放。保留首次审核人与时间，不覆盖。 |
| C12 生成期间撤权 | 模型调用前鉴权；调用结束、保存可供用户读取的建议前再次统一鉴权，并用短 DB 事务约束该保存步骤；调用模型仍不在写事务内。已撤权不返回/登记为该用户可用的待确认建议，只按必要失败/安全证据处理，不把生成结果继续泄漏给前端。尚有权但来源变化时不保存成“可直接应用”的有效建议。后续任何查看/确认再鉴权；无法撤回撤权前已经合法发出的请求，不声称可以。 |

4. 不新增 task/service.ts、不改其他旧模块；shared/app/routes/schema/authz 仍由 B 单写。若当前 task 实现导致上述范围不足，先报告并申请扩展，不自行外溢。
