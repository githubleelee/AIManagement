# Sprint 1 项目统一交接方案

> 用途：为下一位开发者/集成人员交接 Sprint 1 当前实现状态、不连贯项和统一验收路线。
> 范围：只收敛 Sprint 1，以项目可运行、前后端与接口契约一致为验收目标。本文件是盘点与计划，不代表下列工作已经执行。
> 盘点基线：`feat/sprint1-wrapup`，提交 `447c833`；`main` / `origin/main` 为 `cb2670e`。本轮刷新了远端并快进本地 `main` 43 个提交；收尾分支与其远端同名分支一致，且在 `main` 之上多一个收尾提交。

## 当前结论

Sprint 1 的后端、前端骨架及 US-05 前端收尾都存在于当前收尾分支。已知远端状态下，工作区原先干净，收尾分支比 `main` 多一个提交；`main` 已从落后 43 个提交快进到 `cb2670e`。收尾分支尚未合入 `main`，因此后续整合前应先做契约和运行验证，再采用快进/合并请求等团队认可的方式整合。

本次盘点和 Git 同步没有运行测试、类型检查或构建，不能据此宣称当前项目已通过运行验收。

## 发现的不连贯处

### 1. 当前状态分散在不同时间点的文档

- `docs/handoff.md` 描述较新的交接状态：US-05 后端已在 `main`，前端任务界面在 `feat/sprint1-wrapup`，等待整合。
- `docs/T2-integration.md` 是较早的 T2 集成快照，仍称 US-05 尚未进入 `main`，并把任务敏感可见性接入列为待办。它没有醒目标记“截至哪个提交”，读者容易把历史状态当成现状。
- `docs/frontend-routes.md` 的路由表仍把需求层级、需求详情、项目任务标为占位页面；当前实现已包含需求页面和任务页面，handoff 也记录了这些页面的完成情况。

**影响：** 接手者无法只凭文档判断哪些是冻结的初始设计、哪些是历史记录、哪些描述当前代码。

### 2. 路由注册代码中有过时的合入注释

`src/routes.ts` 已调用 `registerTaskRoutes(app, context)`，覆盖任务端点 24–29；端点 30 由授权模块提供。但紧接着的注释仍写“尚未合入 main”。当前 `main` 已包含任务路由注册，这句话与代码和分支状态不符。

**影响：** 阅读者可能误以为后端任务路由还未进入主干，重复接入或漏做验证。

### 3. handoff 对主体完成与收尾待合并的口径不够明确

`docs/handoff.md` 将 US-01、US-03 标为已合入，同时注明 US-01 的 AC-04 改动仍在收尾分支；US-05 后端已合入、前端待合入。该划分本身可成立，但表格没有清楚区分“故事主体已交付”和“当前分支的追加收尾尚未合入”。

**影响：** 读者可能把功能主体已进 `main` 误解为该故事的所有最新改动都已进 `main`。

### 4. 共享契约有规则，但当前状态没有单一维护入口

项目规则要求共享文件由指定负责人维护、契约变更先提出并通知；而集成状态分别出现在 handoff、T2 说明、前端路由说明、代码注释和 AI 互动记录中，缺少一处同时列出用户故事、端点、页面、当前分支和验收状态的索引。

**影响：** 多人并行时容易产生重复实现、漏接端点、文档误导和合并前后状态不一致。

### 5. “已接通”与“已验收”需要分开记录

handoff 列有 Sprint 评审、回顾、自评和演示录屏待办，也指出前端目前没有自动化测试、需手工走查。接口代码已存在不等于用户流程、构建和验收材料都已确认。

**影响：** 可能把代码完成度当作 Sprint 验收完成度。

## 建议的统一升级方案

### 阶段 A：建立当前状态基线

1. 以本交接文档及一份短小的“当前实现状态表”记录事实；每次更新标注日期、分支和提交。
2. 将文档分为三类并明确标注：
   - **冻结契约/基线**：保留为 Sprint 1 的设计决策依据，不冒充当前实现快照。
   - **历史集成记录**：保留原始过程和当时验证结果，标题或开头标明适用提交/时间及“历史快照”。
   - **当前实现与验收状态**：只由指定负责人维护，记录各故事、端点、页面、分支和验收证据。
3. 更新 `docs/handoff.md` 与 `docs/frontend-routes.md` 中过时的状态描述；保留历史决策时，改为指向当前状态表。
4. 删除或改写 `src/routes.ts` 中“任务路由尚未合入 main”的过时注释，并明确端点 30 的唯一注册归属，避免重复注册。

### 阶段 B：按垂直链路核对契约和实现

逐条核对登录、项目及成员角色、需求层级、敏感可见性、任务创建/编辑/删除、故事内任务列表和项目任务列表。每条链路确认：

- 路由只注册一次，前端使用约定的 `/api` 入口；
- 请求/响应字段、状态枚举、日期格式和错误信封符合 `docs/sprint1-spec-interface-contract.md`；
- 角色权限与项目隔离在服务端生效；
- 敏感对象在列表、详情、计数和负责人过滤场景都按契约处理；
- 文档记录的页面状态与实际页面一致。

遇到契约冲突时，按项目既定流程提出变更、通知受影响模块、由单一负责人修改并记录，不让不同模块各自解释契约。

### 阶段 C：完成运行验收与收尾整合

1. 在干净工作区按 README 完成依赖、环境变量和数据库迁移准备。
2. 运行 `npm run typecheck`、`npm test` 和 `npm run build`，记录命令、结果、失败项与修复提交；随后手工走查主要用户流程和权限边界。
3. 对失败项按归属模块建立修复清单，不通过删除或放宽既有契约断言来制造通过结果。
4. 将 `feat/sprint1-wrapup` 与已更新的 `main` 对照并整合，复核合并后的工作区、提交和测试证据；更新 handoff 与当前状态表。
5. 课程评审、回顾、自评和演示录屏不作为本轮代码统一验收的阻塞项；如课程仍要求这些材料，另行建立交付任务。

## 推荐的完成判定

只有同时满足以下条件，才将 Sprint 1 标记为统一完成：

- 当前状态文档、路由表和代码注释彼此一致，历史记录有明确时间/提交边界；
- 用户故事到前端页面、后端端点和契约字段的链路核对完成；
- 类型检查、全量测试、生产构建均有最新记录；
- 关键角色和敏感可见性流程完成手工走查；
- 收尾改动完成团队认可的主干整合，交接记录反映整合后的提交。

课程表格与演示材料另行记录完成状态，不以其替代代码和运行验收。
