## 三、工单

### T5-01 — 任务能建出来，并从用户故事里看见它

**要构建什么**

在用户故事详情页新建一个任务，填标题、负责人、验收人、计划起止日期，保存后任务出现在该用户故事的任务列表里；刷新后仍在。这是 T5 的行走骨架 —— 用来证明「Task 表 → 接口 → 权限 → 界面」这条路径是通的。

**本工单只做形状校验**，业务规则留 T5-02：
- 必填（标题、负责人、验收人、计划开始、计划结束）
- 标题长度上限
- 日期格式 `YYYY-MM-DD`

**明确不做**：成员归属校验、验收人 ≠ 负责人、结束 ≥ 开始、任务编辑、删除、敏感标记、按负责人过滤。

**阻塞于**：T0 收口工单（T0-06）
**演示另需**：US-03 的用户故事创建、US-01 的成员列表（见 §1.2）

- [ ] 能在用户故事详情页新建任务，保存后出现在该故事的任务列表中
- [ ] 任务列表按计划开始日期升序展示；计划开始相同则按创建时间升序
- [ ] 接口要求 `task.write` 权限：项目成员（`MEMBER` / `VIEWER`）调用被拒绝，界面不出现新建入口
- [ ] 非项目成员访问用户故事下的任务列表被拒绝
- [ ] 计划时间以 `YYYY-MM-DD` 字符串原样进出，不被时区转换
- [ ] 每条形状校验各有一条反例测试（必填缺失、标题超长、日期格式非法）
- [ ] 任务的 `status` 创建时默认为 `TODO`，`isSensitive` 默认为 `false`
- [ ] 任务的 `projectId` 从所属用户故事推导，**不接受请求体传入**

### T5-02 — 让任务分配真的可信

**要构建什么**

把「谁来做、谁来验、什么时候做完」这三件事变成不可绕过的约束：负责人与验收人必须是本项目成员；验收人不能与负责人是同一人；计划结束不能早于计划开始。拒绝时要给出可被测试断言的错误码。

**这是团队决策 3 的落地工单**（验收独立性与负责人互斥），也是 Sprint 1 里最容易被 AI 智能体"顺手放过"的一条 —— 审查时重点看服务端，不要只看前端下拉限制。

**阻塞于**：T5-01

- [ ] 负责人不在本项目成员中 → 拒绝，字段码 `NOT_PROJECT_MEMBER`
- [ ] 验收人不在本项目成员中 → 拒绝，字段码 `NOT_PROJECT_MEMBER`
- [ ] 验收人与负责人为同一人 → 拒绝，字段码 `ACCEPTOR_EQUALS_OWNER`
- [ ] 项目成员少于 2 人时创建任务 → 拒绝，字段码 `INSUFFICIENT_MEMBERS`（否则不可能满足上一条）
- [ ] 计划结束早于计划开始 → 拒绝，字段码 `END_BEFORE_START`
- [ ] **三条业务规则收敛到一个共用校验函数**，创建与编辑走同一条路径（为 T5-03 做准备）
- [ ] 校验顺序：必填与成员归属先于「验收人 = 负责人」比较（避免对空值做相等判断）
- [ ] 每条规则至少一条反例测试，且断言的是**错误码**而不是错误文案
- [ ] 业务规则**不走 Zod**，由处理器抛出 `AppError`（契约决策 I-2b 的职责边界）

### T5-03 — 任务详情、编辑与状态推进

**要构建什么**

点开一个任务能看到全部字段；能修改标题、描述、负责人、验收人、计划时间；能把状态从未开始推进到进行中再到已完成。改完之后，用户故事下的任务列表与本页显示一致。

**本工单的核心风险是「部分更新合并语义」**：修改负责人时必须拿**现有的验收人**做比较，而不是只看请求体里出现了什么字段。只校验请求体的实现会放行最容易发生的绕过路径（把负责人改成当前验收人）。

**阻塞于**：T5-02

- [ ] 任务详情返回全部字段，且内嵌负责人与验收人的简要信息（id、账号、显示名）——**前端不需要为每个任务再发一次用户请求**
- [ ] 可编辑字段：标题、描述、负责人、验收人、计划开始、计划结束、状态
- [ ] **部分更新**：请求体中未出现的字段保持原值
- [ ] **验收人 ≠ 负责人 在编辑路径同样生效**，且三条路径都要测：
  - 只改负责人使其等于现有验收人 → 拒绝
  - 只改验收人使其等于现有负责人 → 拒绝
  - 同时改两者使其相等 → 拒绝
- [ ] 校验以「现有值 + 请求体覆盖」的**合并结果**为准，**不得只校验请求体中出现的字段**
- [ ] 状态可调整为 `TODO` / `DOING` / `DONE`；用 `BLOCKED` / `SUSPENDED` / `CLOSED` 提交 → 拒绝
- [ ] 任务不可跨项目挂载（用户故事与任务的 `projectId` 必须一致）
- [ ] 任务响应不含 `isSensitive` 的修改入口 —— 该字段只能通过 T5-05 的独立端点修改
- [ ] 只有 `PM` 可编辑，`MEMBER` / `VIEWER` 只读

### T5-04 — 删除任务，且不留下孤儿数据

**要构建什么**

能删掉一个任务；删掉之后它不再出现在任何列表里。同时保证反过来也成立：**只要用户故事下还挂着任务，这条用户故事就删不掉**。

**本工单有一条全文档唯一需要人工保证的引用完整性**：`ObjectVisibility` 是**多态表**（`objectId` 同时指向用户故事与任务），数据库**无法为它建真实外键**。所以删除任务时必须由代码在同一事务内手动清理它的可见性记录。漏掉这一步不会报错，只会留下悬空数据。

**阻塞于**：T5-03

- [ ] 删除任务后，它不再出现在任务列表、任务详情与任何计数中
- [ ] **删除任务时，同一事务内清理该任务的 `ObjectVisibility` 记录**
- [ ] 有任务挂载的用户故事不可删除 → 拒绝，字段码 `HAS_CHILDREN`
- [ ] 该删除保护由数据库外键 `Restrict` 保证，**不依赖应用层判断**
- [ ] 删除一个不存在的任务 → 与「无权限」返回完全一致的响应
- [ ] 只有 `PM` 可删除
- [ ] 有测试断言：删除任务后 `ObjectVisibility` 中对应记录条数为 0

### T5-05 — 敏感任务只对指定成员可见

**要构建什么**

项目经理可以把某个任务标记为敏感并指定可见成员；被授权成员能看到它，其他成员在**任何地方**都看不到 —— 列表里没有、详情打不开、计数里不计入。

**这是全项目最容易漏的泄漏入口**：任务可见性有三条独立查询路径（用户故事下的任务列表、任务详情、按负责人过滤的列表），**任何一条漏掉过滤都会泄漏**。

**阻塞于**：T5-04、T0-05（`can()` 与 `visibilityScope()`）、US-02 的敏感标记与白名单机制工单

- [ ] `PUT` 敏感可见性端点：全量覆盖（请求中的可见成员名单替换原有名单，不追加）
- [ ] 只有 `PM` 可设置敏感与可见名单；`sensitivity.manage` 权限生效
- [ ] 可见名单中含非本项目成员 → 拒绝，字段码 `NOT_PROJECT_MEMBER`
- [ ] 关闭敏感标记后，全项目成员恢复可见
- [ ] 把某成员移出可见名单后，该成员的**下一次请求即被拒绝**，不需要重新登录
- [ ] **三处查询路径全部接入可见性作用域**：用户故事下的任务列表、任务详情、按负责人过滤的列表
- [ ] 列表过滤在**查询层**完成，**不得使用「取出全量再在内存里过滤」** —— 内存过滤会在统计计数上泄漏敏感任务的存在性
- [ ] 未授权成员直接请求敏感任务 id → 返回与「任务不存在」**完全一致**的响应，响应体不含任务任何字段
- [ ] 无权成员的 404 文案不含「无权限」「敏感」等字样
- [ ] 敏感标记的变更写入审计记录（操作人、时间、对象、变更前后值）
- [ ] 有测试断言：未授权成员在「列表 / 详情 / 计数」三处均不可见

### T5-06 — 按负责人查看任务（P1，可降级）

**要构建什么**

项目经理按成员筛选，看到某个人当前被分配了哪些任务，用来判断谁手上活多。

**本工单最容易踩的坑与 T5-05 相同**：这是一条**独立的查询路径**，同样必须接入可见性作用域。若排期不足要砍掉这个工单，**应整个移除该端点，而不是保留一个不过滤的版本**。

**阻塞于**：T5-05

- [ ] 可按负责人筛选任务列表
- [ ] 负责人不是本项目成员 → 拒绝，字段码 `NOT_PROJECT_MEMBER`
- [ ] 结果按计划开始日期升序
- [ ] **该查询同样接入可见性作用域**（与 T5-05 的三处路径并列，是第四条）
- [ ] 只有项目成员可访问；非项目成员被拒绝
- [ ] **降级说明**：若砍掉本工单，必须同时移除该端点，不得保留未过滤版本

## 五、每个工单的通用要求（不要漏）

1. **接口契约是权威来源**。契约在 Sprint 1 期间冻结，变更走「提出 → 受影响模块确认 → 单人修改 → 通知」四步。发现契约有问题，优先按契约实现并在回顾中提出。
2. **测试与实现同步写**（DoD 要求「有基本测试」）。唯一 seam 是 **HTTP 接口层**；不要为内部函数单独建测试层。测试用数据工厂自建数据，不依赖全局种子。
3. **关键函数与模块写注释**（DoD 要求「有代码注释」）。
4. **人工审查 AI 生成的 diff 后合入**（DoD 要求「代码已审查」）。审查时把「服务端强制校验」列为必查项 —— AI 在鉴权与业务规则处最容易只写前端限制。
5. **每个工单至少产生 1 条 AI 互动记录**，按表 5 的 7 列格式追加到 `docs/ai-interaction-log.md`：只追加、不改已有行、实时记录不得事后补造。
6. **文件所有权**：只在自己模块的目录内新增文件；共享类型、数据库 schema、路由注册表三处只读，改动需通知技术负责人。
