## 一、请在 #31 提案中增加的内容

在你已收到的最小 AI 端口请求（B1 输入与建议输出 / B2 运行模式与数据边界 / B3 组装契约 / B4 最小示例）基础上，把**存储与处置**一并提案，至少包含：

| 类别 | 需要的字段或语义 |
|---|---|
| 场景标识 | 场景 / 分析类型，需能区分 #31 需求拆解、#32 排期建议、#33 质量 / 进度 / 风险 / 效率分析 |
| 输入追溯 | 输入范围、关键数据快照与生成时间 |
| 模型追溯 | 模型或桩标识、实际可得的版本（取不到记「未提供」）、运行模式（`stub` / `api`） |
| 建议内容 | 建议结构与内容、错误表示、请求 ID |
| 处置 | 处置状态（待确认 / 采纳 / 修改后采纳 / 拒绝）、处置人、理由、人工修改、最终应用结果 |
| 统计 | 支撑「采纳质量」统计所需的最小信息（是否被采纳、是否需大幅修改、是否被拒绝） |

**说明**：字段命名与类型由你提案，B 与你核对后才作为契约，不要把候选字段名当成已批准；也不要求你现在就写完整持久化与迁移。

## 二、共享要求

- 这套存储**必须同时服务 #32 与 #33**，不是需求拆解专属；A 会提交 #33 的字段需求，C 会提交 #32 已确认的记录字段，请一并纳入。
- 处置权限统一为**仅 PM**；MEMBER / VIEWER 只读。你只提供能力与字段，不在框架里私写业务角色判断，由统一 `can()` 判定。
- 生成与应用分离：生成阶段在写事务外调用模型并保存建议；处置阶段应用已保存的建议，不重新生成替换待确认内容。
- 桩与真实 API 必须可辨识，**不得在 API 失败时静默退回桩并冒充成功**。
- 继续按 `docs/role-d-start-confirmation.md`：公共类型与端口放 `src/shared/`、运行时由 `src/app.ts` 组装注入；实现写在你自己的目录内；公共文件由 B 落，你只提交提案或补丁；不跨模块调用 service。

---

## 三、不能做的事

- 不新建第二套建议存储，也不把存储做成只有需求拆解能用的形状。
- 不代 A / C 实现分析、排期或采纳应用的业务逻辑。
- 不提交真实凭据；前端不持 key，后端从 env 读；敏感对象默认不入上下文；本轮范围变更**不得宣称满足原 AC13**。
- 不以「已实现 / 已接入」描述尚未运行的接口草案。
