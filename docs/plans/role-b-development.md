## 一、目标与执行优先级

完成 B 域三个执行票，并统筹相关契约、授权及公共文件交付。

**建议主线（优先级，不是硬依赖）：**

> **#24 最小契约梳理 → #27 成员负载 → #26 甘特图 → #25 故事看板**

> 本轮口径同步（2026-10-17）：该顺序只表示**优先级**，**不构成跨票硬依赖**。三票在独立目录（`workload/`、`gantt/`、`board/`）可并行推进设计与实现；公共文件由 B 单写、组件按就绪挂载，**不整模块等待**。详见 §二 与 `docs/tasks/role-b-development.md`。

执行约定：

- #24 先明确首票所需的最小契约，之后贯穿全程；**不等全部议题确认才开工**。
- 优先提前登记 #26 的字段、事件接口与公共文件改动，但不以此阻塞其他票已明确的工作。
- 独立文件、目录可在各自实施范围获批后并行开发；先划清写入边界，同文件不并发修改。**公共文件仍由 B 单写**。
- 被阻塞时继续不受影响部分；不得凭优先级新增硬依赖，也不得凭并行约定扩大本轮仅文档的实施授权。
- 批准本计划不等于批准未决业务规则，也不自动授权开始编码。

| 阶段 | 工作 | 原估算 |
|---|---|---:|
| P0 | #24 最小契约及持续协调 | 2 人日 |
| P1 | #27 成员任务图与负载 | 4 人日 |

## 二、当前基线与不可越过的边界

计划编制时已核对的本地实现事实（每票开工前仍须复核最新 main）：

- 任务目前仅有 `TODO / DOING / DONE`，没有 `CLOSED`。
- 故事状态为 `DRAFT / PLANNING / DONE`，与任务状态不是同一模型。
- `Task` 已有计划起止日期；故事没有独立计划日期字段。
- 尚无 `Milestone`、`TaskDependency` 表。
- 既有故事状态 PATCH 没有审计、事件调用，#25 必须补齐，不能假定已经具备。
- 当前写权限主要限 PM；成员是否能修改故事状态仍待 C11。
- 新模块直接读库，不调用其他业务模块 service；敏感过滤必须进入数据库查询，列表与计数使用相同权限条件。

**文件边界（2026-10-17 更新，来源见 `docs/role-d-start-confirmation.md` 与 `DECISIONS.md`）：**

| 类型 | B 的处理方式 |
|---|---|
| 新业务模块及页面 | 在 `workload/`、`gantt/`、`board/` 独立目录实现 |
| `src/shared/*`、`src/db/schema.prisma` 及迁移、`src/routes.ts`、`src/app.ts`、前端公共骨架、`docs/frontend-routes.md`、`var/uploads` 的 `.gitignore` | 项目负责人已授权 ROLE-B = `githubleelee` **统一单写 / 合入**；不再“提申请等原 owner” |
| `src/modules/authz/permissions.ts`（权限 / 签名） | **排除**在本次授权外，须按适用契约另行确认 |
| 既有 requirement / task / project / authz 等业务文件 | 先获原 owner 对**具体文件 / 范围**的书面授权，再实施；不得旁路新建镜像写路径 |
| `test/factories.ts` | 只读，不修改 |

> 授权来自**项目负责人**，不代表原技术负责人 / 前端骨架原修改人已单独表态，也不扩大其他业务域的修改权限。另已授权 B 在 `RequirementDetailPage.tsx` / `TaskSection.tsx` / `AppLayout.tsx` 最小挂载 D 的 AI / 附件 / 通知组件；仅此接入不需额外旧 owner 同意，超范围业务修改仍申请。本轮仅实施文档同步与相关工单说明，编码需另获授权。

本计划不接管 D 的 AI / 通知 / 附件 / 事件业务实现，也不包含 C 的在线 UML 或 A 的任务验收业务；新增公共接入另列任务，B 不代其他角色实现或确认其业务规则。

## 三、分阶段开发安排

### P0：#24 最小契约与开工准备

**目标：**让 #27 有明确、安全的开工范围，同时提前疏通 #26、#25 的外部条件。

#### 开发前工作

1. 复核最新 `main` 的实际实现与三份既有规则文档，确认没有重复建设。
2. 整理 B 域契约清单；每项记录：
   - 涉及工单和待决定问题；
   - 提议方案与待确认人；
   - 当前状态及书面证据链接；
   - 影响开发的部分和影响最终验收的部分。
3. 准备 B 域确认与旧业务模块**具体文件授权**的留言草稿；已授权的公共文件由 B 直接单写，无需等待外部 owner。由用户确认后再发布。
4. 先明确 #27 的数据字段、可见性和状态消费方式。
5. 由 B 作为公共层单写人准备 #26 的模型、共享类型、路由及前端挂载，允许 schema 小批次顺序合入。
6. 向 #37 对接事件信封、发布接口、注入位置、幂等和敏感载荷约束；不直接调用 D 域业务 service。

#### 必须跟踪的事项

| 契约／申请 | 涉及票 | 所需结论 |
|---|---|---|
| 六状态落地及历史数据处理 | #27、#26 | 状态映射、迁移、转换、授权、单写人；**不把 DONE 当 CLOSED** |
| C6 汇总权限 | #27、#26 | PM／member／viewer 的范围、全局与可见基数语义 |
| C2 FS 放行 | #26 | 前置 DONE 还是 CLOSED 才允许后置开工 |
| 甘特聚合口径 | #26 | 故事日期与进度、无任务故事、里程碑汇总等边界 |
| FS 执行落点 | #26 | 真正的任务开工入口如何执行约束；涉及旧文件时明确 owner 与授权 |
| 公共事件接入 | #26、#25 | 放置位置与 app 组装已确认；具体端口字段、签名及发布失败处理待 D 提案 |
| C11 故事操作授权 | #25 | 成员能否改状态，是否扩展 Action |
| C13 旧模块授权 | #25 | requirement 状态写路径的具体可修改文件与范围 |
| C5 UML 交互 | C 域协作 | B 参与协调，不纳入 B 的实现主线 |

**阶段检查：**能够明确指出 #27 哪些部分可做、哪些只能设计、哪些暂不能验收。其他域未确认的事项继续保留，不代勾完成。

### P1：#27 成员任务图与负载

**分支：**`feat/US07-member-workload`

**主要目录：**`src/modules/workload/`、`web/src/pages/workload/`

#### 开发步骤

1. **接口设计**
   - 明确成员列表、负载摘要、成员关联任务及详情的数据契约。
   - 核对与个人工作台的一致性要求。
   - 对六状态尚未落地的部分保留接口设计，不另造“未关闭”替代规则。

2. **后端只读查询**
   - 校验项目访问与成员身份。
   - 直接查询成员、任务与授权范围。
   - 在查询层排除无权敏感对象。
   - 负载计数和任务清单复用同一筛选口径。
   - 明确无任务成员、空列表等展示边界，不擅自扩展协作人模型。

3. **前端页面**
   - 展示成员及负载、成员—任务关联。
   - 点击成员查看任务状态和计划时间。
   - 补齐加载、空态、错误态及无权限反馈。
   - 由公共骨架单写人（B，经项目负责人授权）添加页面挂载。

4. **验证与交付**
   - 模块测试覆盖计数／清单一致、跨项目、敏感过滤和四类角色。
   - 浏览器走查“负载图 → 成员详情”。
   - 提供 #32、#33 可消费的数据契约与样例，不替它们实现 AI 逻辑。

#### 完成检查

- 对照 #27 AC1–AC6 留证。
- 无权任务既不出现在列表，也不增加计数。
- `DONE` 不被误视为验收关闭。
- 六状态或 C6 若仍阻塞相关验收，明确标记未完成，不用 mock 冒充通过。

### P2：#26 甘特图、里程碑与 FS 依赖

**分支：**`feat/US06-gantt`

**主要目录：**`src/modules/gantt/`、`web/src/pages/gantt/`

#### 开发步骤

1. **敲定模型与接口**
   - 明确需求、任务、里程碑、依赖的关联关系与返回结构。
   - 作为公共层单写人落地 `Milestone`、`TaskDependency` 字段、约束、索引及迁移（小批次顺序合入）。
   - 明确故事时间／进度汇总、空值、无任务及部分可见时的口径。
   - 不自行给故事新增独立排期状态。

2. **聚合读接口**
   - 提供需求、任务、里程碑和 FS 依赖数据。
   - 支持故事展开关联任务。
   - 统一处理授权过滤，避免通过依赖、汇总或里程碑泄漏敏感对象。
   - 与任务视图按同账号、同授权视角核对。

3. **里程碑与依赖写操作**
   - 按确认后的授权规则实现。
   - 仅接受 FS，拒绝自依赖、环和跨项目依赖。
   - 处理任务里程碑及汇总要求。
   - 自域发布里程碑／计划变更事件，遵守确认后的公共接口。

4. **落实 FS 开工约束**
   - 按 C2 结论实施。
   - 约束必须覆盖真实任务开工路径，不能只在甘特页面禁用按钮。
   - 若涉及既有任务模块，先落实文件授权与实施归属，不新增旁路更新入口。

5. **前端甘特**
   - 时间轴同时展示需求、任务、里程碑。
   - 支持故事展开、任务计划时间及汇总进度。
   - 展示 FS 关系、必要的错误反馈和空态。
   - 不做复杂拖拽、自动调度或其他依赖类型。

6. **验证与交付**
   - 覆盖汇总、里程碑、FS 放行、环、跨项目和敏感过滤。
   - 浏览器验证展开、汇总及里程碑展示。
   - 向 C 域交付 #32 所需数据契约，不形成反向依赖。

#### 完成检查

- 对照 #26 AC1–AC7 留证。
- C2 未确认时，FS 放行相关 AC 不通过。
- 模拟事件仅用于模块验证；跨域真实消费需要真实联调证据。
- schema、类型及路由变更均有公共层单写人（B，已获授权）留痕。

### P3：#25 故事看板

**分支：**`feat/US04-story-board`

**主要目录：**`src/modules/board/`、`web/src/pages/board/`

#### 开发步骤

1. **只读看板**
   - 固定展示 `DRAFT / PLANNING / DONE` 三列。
   - 根据需要提供聚合读接口，不复制 requirement service。
   - 查询层过滤敏感故事，列计数与卡片列表一致。

2. **状态调整**
   - 复用既有 `PATCH /stories/:storyId`。
   - 按 C11 结论控制操作，服务端继续通过 `can()` 判权。
   - 不新增看板私有状态或镜像写入口。

3. **补齐旧写路径**
   - 在 C13 授权范围内补审计，记录 who／when／before／after。
   - 在状态变更成功后，按已确认的事件契约发布事件。
   - 明确写入、审计、事件失败时的一致性要求后实施，不凭空规定策略。

4. **跨视图同步**
   - 更新后重新拉取，核对地图、详情及统计。
   - 需要改他人页面时先申请，不顺手修改旧页面。

5. **验证与交付**
   - 覆盖状态更新、审计、越权、非成员和敏感计数。
   - 浏览器验证“看板改状态 → 地图／详情同步”。

#### 完成检查

- 对照 #25 AC1–AC6 留证。
- 审计、事件来自真实状态写路径。
- 不通过看板绕过 `requirement.write`。
- C11 或 C13 未落实时，不实施受影响的写路径。

## 四、每票统一执行与验收流程

每次开始具体任务前：

1. 由用户确认本票方案及授权范围。
2. 从最新 `main` 建独立短分支／worktree。
3. 核对适用契约、文件边界和逐条 AC；由执行票负责人处理 `needs-confirmation`。
4. 仅实施当前票；出现新业务规则、跨权限边界或旧业务模块改动，暂停该部分并申请；已授权公共文件由 B 单写。

每票交付时：

- 本模块针对性测试，不默认跑全套。
- 执行 `npm run typecheck`。
- 界面票提供浏览器主链路、越权及敏感场景证据。
- 使用真实接口验证；mock 不作为最终验收证据。
- 提供 AC—证据对应表、文件变更清单、契约／授权链接和剩余阻塞。
- PR 只关联本票；不自动合并、关闭旧工单或替其他角色确认完成。
