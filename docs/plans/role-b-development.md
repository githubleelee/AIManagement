### 3.2 #32 限定口径

- **AI 只读消费 + 受控应用**：#32 生成阶段只读消费 `#26 / #27` 数据；人工确认后可经**统一受控路径**修改 `TODO` 任务的 `planStart / planEnd`。此处「不改 #26 / #27」应理解为**不直接修改派生聚合 / 依赖 / 里程碑**，**不是禁止已授权的日期应用**；应用后 B 甘特 / 负载随原任务数据自然更新，而非由 #32 改派生结构。
- **可应用字段**：仅 `TODO` 任务的 `planStart / planEnd`；**不**改负责人 / 验收人 / 状态 / 依赖 / 里程碑。非 `TODO` 只提示，不静默改写。
- **硬阻断 vs 仅提示**（写入验收）：硬阻断 = 日期倒置、`TODO` 新开始早于北京时间今天、违反 FS 计划约束、非 `TODO` 或越字段写；仅提示 = 同一人任务日期重叠、新结束晚于原计划、超过已有关联里程碑日期；无关联里程碑不编造、不自动改里程碑；负载只展示分布，不设「超过 N 即过载」阈值。
- **PM-only 权限**：仅 PM 可生成 / 查看 / 采纳 / 修改后采纳 / 拒绝 / 查看审计；MEMBER / VIEWER 不开放，只能查看既有、且其有权限的正式任务计划。未登录 401、对象不可见 404、可见无操作权 403。
- **权限落地**：B **最小修改** `src/modules/authz/permissions.ts` 及必要共享 `Action` / 对象 scope；若有其他写者先登记排他窗口，未将整个 authz 或其他票权限移交给 B。统一走 `can()` / `visibilityScope()`，业务不私写角色判定；**须覆盖读取 / 审计操作，而非只把 write 加入动作集合**。每次请求及确认 / 重试都重新鉴权，撤权即时收敛。
- **`task/` 限范围授权**：C 在 B 登记具体文件 / 范围并完成现写者交接后的独占窗口内，最小改 `src/modules/task/routes.ts`、`rules.ts` 及本域测试，用于统一计划写路径 / 复用原约束 / 整份事务应用；**不再额外等待原 owner 重复同意**。该例外**不覆盖** B 甘特的旧模块写入口，也不覆盖其他票；不另建旁路、不调 `task service`；若 A 持锁，先等其当前小任务合入后交接，不假定空闲。

## 四、公共读 / 写端口与事务 / 鉴权协议（待提案确认）

`#32` 的落地方式：**C 实现业务 / 整份原子写 / 快照 / 幂等，B 只落公共声明 / 模型 / 权限 / 组装 / 挂载**。因此在 B 组装公共端口前，先就下列事项形成提案并书面确认，**不自行选择具体签名或架构**：

1. **事务内鉴权与规则复用**：现有 `createAuthorization(prisma: PrismaClient)`、内部 helper 与 `assertTaskAssignment` 硬编码 `PrismaClient`，无法直接接 `Prisma.TransactionClient`。需明确如何让统一鉴权 / 任务规则在**同一事务内**复用，不跨模块调用 `service`；受控应用的最终鉴权与约束复核须在同一事务。事务前可做入口检查，但不能仅依赖它替代事务内复核。**具体 `Pick` / `union` 签名待提案核对，B 不擅定。**
2. **应用端口协议**：公共读 / 写端口、事务边界、C 业务写路径与公共组装的分工；`task` 无 `service.ts`，规则在 `routes.ts` / `rules.ts`，须在受控路径内复用而不新建镜像入口。
3. **快照与有效权限语义**：snapshot / fingerprint 的数据定义、比对范围与「有效权限」如何参与过期判定。
4. **唯一处置与冲突**：一份建议只允许一个最终处置；相同请求重试返回已有结果；**相同请求重试但内容不同**、并发处置等冲突语义需在接口层明确。
5. **仍未冻结项**：幂等键、hash 字段、`outbox` 等事件提交架构、前端 URL 等**细节不由单方拍定**，由 B / C / D 提案核对后再落。

生成与应用分两阶段：生成阶段在数据库写事务外调用模型，保存建议 / 输入快照 / 生成记录；确认阶段只应用已保存建议或 PM 允许的日期修改，**不重新生成**；每次重试先鉴权；实际参与基数与「可见范围」如实标注。
